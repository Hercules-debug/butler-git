# butler-git —— git 原生的节点门禁

> 这是**重新写的**实现,不是在 `../butler-demo` 上改的。
> 旧的核心是「文件系统 diff + 断言」,这一版是「git 树 + 进程声明 + 验证程序」。

**零依赖。** 只需要 `node` 和 `git`。

---

## 跑起来

```bash
node test/run.mjs        # 27 条负向验收
node test/plugin.mjs     # 插件自测(12 条)
# 或
npm test
```

单步:

```bash
BG="node bin/bg.mjs"

$BG init                                       # 取基线
$BG check  --file c.json                        # 只检查门禁够不够格
$BG declare --file c.json                       # 声明/改写一个节点
$BG accept n-1                                  # 验收 -> 点亮第一盏灯
$BG view [--live] [--detail n-1]                # 看树(两盏灯)
$BG health                                      # 心跳一行
```

## 两盏灯

**一个节点两盏灯,因为它们回答两个不同的问题。**

```
第一盏  通过过没有   读账本,历史事实,不可变
第二盏  现在过不过   跑检查,当下,只是参考
```

| | 第一盏 | 第二盏 | 含义 |
|---|---|---|---|
| `●●` | ✓ | ✓ | 通过过,现在也对 |
| `●○` | ✓ | ✗ | **通过过,但现在已经坏了** ← 回归 |
| `○●` | ✗ | ✓ | 没通过过,但现在能过 |
| `○○` | ✗ | ✗ | 没通过过,现在也不过 |
| `·` | | | 第二盏没算(它是参考,不该让看一眼变贵) |
| `–` | | | 没有门禁 |

### 为什么必须两盏

一盏的时候,"绿"同时在说两件事,于是必然有一件说错:

```
只按"现在符合"算  ->  没有任何验收动作的节点也会显示绿,
                      那把"验收"这个动作本身的价值抹掉了
只按"通过过"算    ->  可以有一棵全绿的树而产品是坏的
```

**第一盏只能由一次郑重的验收点亮**(`accept`),而且点亮后不被后来的改动推翻 ——
因为"当时确实验过"这件事永远为真。

### 第二盏顺带是个定位器

东西坏掉的时候,是**逐节点的第二盏灯**指出位置:

```
root  ○●  整体功能   (能过,但没通过过; ↓ 底下有红的; 人定)
├─ c1  ●●  改 x.py
└─ c2  ●○  改 y.py   (通过过,但现在坏了)
```

**不用猜是哪里坏的。** 心跳也会指名道姓。

## 门禁 = 三部分

```
fs      预期的文件系统情况
        ├ paths  逐条路径断言(直接 stat/读 —— **免疫 .gitignore**)
        └ tree   整个世界必须等于这个 git 树哈希(绝对判据,可选)
proc    进程情况(该在的在 / 该没的没有)
verify  验证程序(跑起来成不成)
```

**三条全过,节点才"现在过"。** 三种结果,不是两种:

```
ok        确实满足
fail      确实不满足(附一条"要求",模型能照着修)
unknown   **不知道** —— 观测能力受限,或这次没查(贵的部分)
```

`unknown` **既不是通过也不是不通过**。它必须能被表达出来 ——
否则"看不见"会被读成"没问题"。

### fs 为什么分 paths 和 tree

```
tree   说"世界和预计**一模一样**" —— 强,但:
         · 失败时只有诊断能救它(所以带 `git diff --name-status`)
         · **.gitignore 的路径它看不见** -> 编译产物不能用它
paths  逐个点名 —— 直接 stat/read,gitignore 免疫,失败可定位
```

**两个都要**,因为它们覆盖不同的东西。这一条是实测出来的:
`build/` 被 ignore 时,树比较对 `build/out.js` 完全瞎,而 `fsExists` 照样看得见。

## 防"白给的门禁"

**判据:门禁是全部断言的合取。如果它在基线时就已经成立,它在开工前就是绿的 —— 等于没有门禁。**

最典型的形态:

```
verify: "true"        <- 永远退出 0
```

它什么都验不了,但报告里它是绿的。实测:

```
$ bg check --id fake --verify true
✗ 验证程序在基线(HEAD)上就已经通过 —— 它区分不了你做没做: true
```

### 必须看合取,不能一条一条看

一条"别破坏 X"的回归断言单独看,在基线本来就通过。
但如果**另一条**要求世界变化,整体门禁仍然有约束力 —— 单条判会冤枉它。

### 为什么它不拖慢常见情况

按**成本**分两段:

```
1. 先看便宜的文件侧。只要有一条在基线**不**成立 -> 立刻返回,不跑命令。
2. 只有文件侧全部在基线成立时,才去跑验证程序(可能很贵)。
```

常见路径 **0.25 秒**。

### 安全网不参与这个判断

`file_absent` / `proc_absent` 基线成立**正是它们的意思**("别留下这个东西")。
一刀切会把"不该留实验文件"这类完全正当的清理约束拒掉。

但**只有安全网也算白给** —— 那种门禁里没有任何会失败的东西。

## 所有权与不可篡改

### 所有权跟作者走

```
owner = "user"   人和模型**约定**的验收(根节点)
                 -> 模型改不动,要人授权(--as-user)
owner = "model"  模型自己拆出来的中间节点
                 -> 模型可以自己改(它改的是**手段**,不是目标)
```

这不是权限洁癖,是结构需要:**门禁同时是规格和检查,所以门禁本身就是唯一的目标物。**

### 两道门

```
1. 通过过的节点,门禁冻结 —— 连人也不能直接改。
   要变,起一个**新节点**把改动做出来(历史不改写,旧节点保持"通过过")。

2. owner=user 且**已经有一份门禁** -> 模型改不动。
   "已经有一份门禁"这个条件很重要:`plan` 先把节点记下来时还没有门禁,
   模型随后补写是**首次定义**,不是改 —— 不该拦。
```

这一条堵的是一个**实测跑通的逃逸路径**:

```
提交门禁 -> 干活让它绿 -> 再提交一份更容易的 -> 原约定蒸发
```

### 改写必须留痕,而且要记门禁本身

只记一句描述的话,**真正要保护的那个东西反而没有痕迹**:

```json
{"type":"node","kind":"改写","node":"m",
 "gate":{...},        <- 现在的门禁
 "prevGate":{...},    <- 改前的门禁
 "by":"model"}
```

### 账本是追加式的

```
accept   追加
retract  追加(不改写那条 accept)
改写     追加(带 prevGate)
```

**没有任何一条操作会动已有的行。** 所以作废之后你能读到的是
"它曾经通过,后来被作废了",而不是"它从来没有通过" —— 后者会丢信息。

## git 原生的两条硬规则

### 1. 观测动作不能改动观测对象

```
workingTreeHash   用**临时索引**(GIT_INDEX_FILE)算 -> 真索引一动不动
baselinePasses    用**临时 worktree** 跑      -> 不碰当前工作区
```

验收之后 `git status` 一字不变(有验收守这条)。

### 2. 工具自己的状态目录必须排除

`.bg/` 里是账本和图 —— **每做一次操作就会变**。不排除的话:

```
任何"世界必须等于这个树"的门禁,永远都不可能通过
```

这不是理论问题,是实测出来的(而且上一个实现正是死在这里)。
判据:**被观测对象里不能包含观测者自己的记录。**

```
git add -A -- . ':(exclude).bg'
```

用 pathspec 排除,不写 `.gitignore`、不碰真索引 —— 不留痕迹。

## 进程侧:只对照声明,不扫描

全表扫描找残留**没有可靠判据**,而**噪声比漏报更危险** ——
噪声会让你开始忽略报告。

所以只做一件事:对照节点**事先声明的** pattern 查。
**已知代价:模型没声明的进程,系统发现不了。**

### "看不见"绝不能变成"不存在"

这是踩过的坑。旧实现里 `cmdline()` 读不到时返回**空串**,调用方当成"进程不存在",
于是:

```
沙箱里 ps 被拒 -> 所有 proc_present 永远找不到目标
                -> proc_absent 永远通过
                -> 不报错,只是安静地给出错误结论
```

所以显式分三种:

```
matched      真的匹配到了
absent       真的没有(读得到命令行,且不匹配)
unreadable   **看不见** —— 观测能力受限,不是事实
```

实测(沙箱里 `ps` 读不到命令行):

```
? proc_present(svc_zz)  1 个候选,但命令行一条都读不到 —— 观测能力受限
```

## 插件

`plugin/index.js` —— 五个工具,给模型用:

| 工具 | 干什么 |
|---|---|
| `node_check` | 写之前自检:这份门禁够格吗 |
| `node_declare` | 声明/改写节点 |
| `node_accept` | 验收:跑完整门禁,全过则点亮第一盏灯 |
| `node_tree` | 看树(两盏灯) |
| `node_health` | 心跳一行 |

### 逻辑只有一份

```
bin/bg.mjs      人用的 CLI
plugin/index.js 模型用的工具
        \       /
         lib/*.mjs      ← **同一套**
```

**这一条是有代价换来的。** 上一个实现把核心写了两遍(Python 一份、JS 一份),
改了一边另一边静默落后 —— 于是"模型用的那半边没有新门禁"。
现在插件**只调 `../lib`**,不起子进程、不重写一份。

`test/plugin.mjs` 里有两条守它:插件不出现子进程调用、必须从 `../lib` 导入。

### 插件不暴露 `as-user`

否则模型就能自己授权自己改人定的验收 —— 那道门等于没有。

## 和 `../butler-demo` 的关系

**这是重新写的,不是在它上面改。**

| | butler-demo | butler-git |
|---|---|---|
| 文件侧判据 | `git status` diff + 子串断言 | **git 树哈希(绝对)+ 直接 stat** |
| 状态 | 一个(达成) | **两盏灯** |
| 验收 | `exit` 判定,`compute_state` 又重算一遍 | **`accept` 点亮,历史不改写** |
| 门禁质量 | 同义反复 / 矛盾 | **+ 非空转(整个门禁在基线成立就拒)** |
| 篡改防护 | 无 | **所有权 + 通过后冻结** |
| 进程看不见时 | 当成"不存在" | **报"不知道"** |
| 实现份数 | 两份(Python + JS),会漂移 | **一份(lib),CLI 与插件共用** |

旧实现里那条 `_set_state` 写了 `终态` 事件,但 `compute_state` **从来不读它** ——
状态每次从断言重算。这一版把这件事理顺了:**终态就是历史事实,读账本。**

## 已知边界(诚实的部分)

1. **.gitignore 的路径对树比较不可见。** 产物那类要用 `fsExists` 直接 stat。
2. **进程侧没有基线快照**,所以 `proc.present` 判不了"基线时是否已经在跑",
   非空转检查对它**弃权**(不据此拒,以免冤枉)。
3. **进程报备制的固有代价**:没声明的进程,系统发现不了。
4. **`verify` 会被真的跑起来。** 它是模型写的命令,在项目的正常工作区里跑
   (`accept` 时),和跑测试没有区别 —— 但要知道它确实执行。
5. **网络副作用**完全在观测之外。这是唯一一个无法验证的维度。
6. **宿主必须有 `pgrep` 和可用的 `ps`。** `ps` 读不到命令行时,进程侧退化成
   "不知道" —— 这是设计,不是 bug,但那意味着进程维度的门禁在那个宿主上不起作用。
