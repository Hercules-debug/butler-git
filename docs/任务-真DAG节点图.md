## 一、这是什么

`butler-git` —— 一个 git 原生的**节点门禁**工具。零依赖(只要 `node` 和 `git`)。

```
节点(node)  = 一个意图:expect + 预期改动 Δ + 检测程序 P
commit      = 达成时留下的证据,不可变
绿          = 一个关于某个 commit 的事实
```

概念细节见 `README.md` / `DESIGN.md`。**先读它们。**

---

## 二、要做什么

改"人的面"里的那张图(`bg html` 的网页版,**主要是它**;终端版能改则改)。

### 四条明确要求

**1. 图是真正的 git DAG** —— 点和线

- **点** = commit
- **线** = git 的父子关系(`git log --format=%P` 给出的 parents)
- **不是**"按某个数值排成一行"

**2. 只画有节点的点;普通提交压成线**

一个真实仓库可能有几千个提交,全画出来是一团糊。

```
● 节点A ─────────────────── ● 节点B     ← 中间没有其他节点:一条线
● 节点C ─┬─────────────── ● 节点D       ← 中间有分叉:要把分叉画出来
          └─────────────── ● 节点E
```

也就是说:节点是**必须出现**的点;它们之间的普通提交换成线。
分叉/合并**必须保留** —— 那是 git 的结构,不能压掉。

**3. 意图结构(谁拆给谁的)用虚线连**

节点之间有两个不同的关系:

| 关系 | 从哪来 | 画法 |
|---|---|---|
| **git 父子** | `git log --format=%P` | 实线(就是上面说的线和点) |
| **意图父子** | 节点的 `parent` 字段 | **虚线** |

两者**不是一回事**,所以线型要分开。同一个节点上可能同时有这两种线。

**4. 点击节点看详情**

点一个点,能看到这个节点的:

```
expect      (要达成什么)
P           (检测程序原文)
P 文件      (P 的脚本在哪 —— 见 nodes.mjs 的 verifyPathOf)
Δ           (预期改动,精确集合)
证据 commit (result)
base        (从哪个 commit 开始)
时间        (声明时刻 / 达成时刻)
状态        (todo / done / abandoned)
```

**5. 颜色区分状态**

```
● 绿(done,有 commit,已验过)
● 进行中(有工作区改动,未提交)
● 待办(todo,还没做)
```

具体什么颜色由你定,但三者要**一眼可分**。

## 三、验证数据的问题(**重要**)

**本仓库的 git 历史是纯线性的** —— 27 个提交,**0 个分叉点**(实测)。

也就是说:**在这里写出来的图,没法验证它是否真的支持分支。**
上一版就是在这个"假直线"上跑通的,所以看起来对。

**所以你至少要造一个有分叉的仓库来验证:**

```bash

git config user.email a@b && git config user.name a

```

在那个仓库里建几个节点(用 `bg plan --as-user`),然后看图 —— **分叉必须画对探**。

## 四、约束(硬性的)

> **⚠️ 修订记录(2026-09-30)**
>
> 原来的第 1 条是「**零依赖**,不引 graphviz / d3 / mermaid / 任何 npm 包」,
> 第 4 条是「HTML 必须**单文件、不联网**」。**这两条已经作废**,由下面
> 修订后的第 1、4 条取代。

> 现有 `lib/html.mjs` 的 `treeSvg` 是**递归树布局**——每个节点恰好一个位置、
> 只认 `children`、父节点居中在子树上方。**这个假设决定了它画不出 DAG**:
> `vis2→graph1→flat1→…` 那条链被摊平成并列方块,根因就是布局算法假设了树、
> 而数据是图。
>
> **实测代价**(人已知情并确认接受):mermaid@10 dist = **3,337,857 字节**,
> 且**打开页面必须联网**。答辩现场断网 = 图打不开。
>
> **没变的东西**:`Δ`/`P`/证据 commit 那套门禁语义一个字没动,
> 这次改的**只是"人的面"怎么把图画出来**。

1. **允许 mermaid(经 CDN)**,但**仅限"人的面"的渲染**。
   不引入任何**需要 `npm install` 才能跑**的依赖 —— 门禁本身
   (`plan` / `status` / `commit` / `abandon` / `approve`)仍然只靠
   `node` 和 `git`。**渲染坏了不能影响门禁。**
   除 mermaid 外不引 d3 / graphviz / 任何别的包。

2. **逻辑只有一份**。`lib/` 是唯一实现,CLI 和插件都调它。
   `test/plugin.mjs` 里有守卫查这件事。

3. **人的面不占模型的工具位**。`bg tree` / `bg html` 是给人用的,
   不要做成模型工具。模型只有 5 个:`node_plan` / `node_status` /
   `node_commit` / `node_approve` / `node_abandon`。

4. ~~HTML 必须单文件、不联网~~ **已作废**。改为:
   **HTML 允许引用 mermaid CDN,不再是自包含单文件。**
   但仍然:**除了 mermaid 不引别的外部资源**;详情面板的 JS 自己写,
   不为了点击去再拉一个库。
   **图必须能在断网时"优雅降级"** —— 打不开图时页面要说清

   上一版最大的问题之一就是**一条验收都没加**。

7. **注释写"为什么"**。这仓库的风格是记录**取舍和踩过的坑**

## 五、上一版错在哪(**先读这一节**)

上一版(在 `lib/html.mjs` / `lib/view.mjs` / `lib/git.mjs` 里,**会被撤掉**)
把图做成了"一条横轴"。它的具体错误:

**错 1:假设 git 历史是一条单链。**

它用这个函数算提交的"位置":

```js
git rev-list --count <sha>..HEAD   ->  一个数字
```

把提交映射成**一个标量**。这在**有分支/合并**的 git 历史里直接崩掉:

```
        A ── B ── C
       /            \
init ──               M  ← HEAD
       \            /
        D ── E ── F
```

A 和 D **没有"谁前谁后"**(它们在两条并行分支上),但那个数字会给出
两个不同的值,于是图**编造了一个顺序**。

本仓库恰好是线性的,所以**看起来对** —— 这是最坏的那种错:**在假数据上跑通**。

**错 2:主干上"每个提交一根竖线",普通提交成了噪音。**

**错 3:把两件事画成两个独立段落** —— 上半段画时间轴,下半段画意图树,
同一个节点出现两次,**没有连起来**。

**错 4:渲染要 53 秒。** 原因:`topoIndex`(3 次 git 子进程)被放在
**排序比较函数**里,27 个提交反复调用 = **131 次子进程**。

**错 5:一条验收都没加。** 测试 73/73 过,但跑的是旧测试,新渲染零覆盖。

## 六、怎么验收

```bash
cd <仓库>
node bin/bg.mjs html          # 生成 .bg/tree.html,浏览器打开
node bin/bg.mjs tree          # 终端版(能改则改)
node bin/bg.mjs serve         # 实时查看器(默认 127.0.0.1:8731)
```

**判断标准:**

- 在**有分叉的仓库**里,分叉画对了(不是编造的顺序)
- 节点之间的普通提交被压成了线,没变成噪音
- 意图父子(git 里没这个关系)用**虚线**能看出来
- 点一个节点,能看到它的 expect / P / Δ / 证据 / base / 时间 / 状态
- 三种状态颜色一眼可分
- **生成** 1~2 秒内完成(不含浏览器下载 mermaid)
- **断网打开时页面说清"要联网",不是一片空白**
- 两个测试套件都过,而且**新加了针对渲染的负向验收**
