# 门禁的输入:工作区还是 commit?

> **状态:未实现。** 这是一次讨论的记录 —— 它指向一个比当前实现更干净的
> 模型,但改动面很大(动的是门禁的**输入类型**),所以先记下来,不动手。
>
> 记下来而不是忘掉,是因为它解释了一件别扭的事:文档里写着
> **"绿 = 一个关于某个 commit 的事实"**,而**实现并不是那样**。

---

## 问题

现在的门禁流程(`nodes.mjs` 的 `evaluateNodeGate`):

```
① treeY = workingTreeHash(dir)      ← 把**工作区**固化成树
② actualDiff = diff(base, treeY)    ← 用那个树算 Δ
③ runVerify(dir, P, { cwd: dir })   ← 在**工作区目录**里跑 P
④ commitTree(dir, { tree: treeY })  ← 提交那个树
```

第 ① 步的目的是"把世界固定下来",因为 Δ 和 P 都需要一个确定的输入。
**但它把"确定的世界"和"工作区"绑死了。**

于是:

- 门禁的输入是**某个目录此刻的状态**,不是一个版本
- 两个 agent 共享工作区时,彼此的改动会互相污染(见 README「并行」那节)
- 父 agent 要批准子 agent 的成果,必须在**子的工作区**里重跑,
  否则算出来的是另一个世界
- "绿"名义上是关于 commit 的,实际上关于"那个工作区在那一刻的样子"

## 另一个形状

```
门禁的输入 = 一个 commit（或一个 tree）
           ≠ 某个目录的当前状态
```

跑法:

```
git worktree add --detach <commit>   ← 临时树,跑完就拆
  → 在临时树里跑 P
Δ 用 diff(base, commit^{tree}) 算     ← 完全不需要工作区
```

**这个能力代码里已经有了** —— `git.mjs` 的 `baselinePasses` 就是
"对某个 rev 跑 P"(它用临时 worktree)。只是**没用在主流程上**。

## 两种形状的差别

| | 现在(工作区) | 改成(commit) |
|---|---|---|
| 门禁输入 | 目录此刻状态 | `commit` / `tree` |
| 需要工作区吗 | 需要(`cwd: dir`) | **不需要** |
| 子向父报什么 | 一段文本 | **一个 commit sha** |
| 父要访问子的工作区吗 | 需要 | **不需要** |
| 同一棵树验两次 | 可能不一致(工作区会变) | **必然一致**(commit 不可变) |
| 并行 | 共享工作区互相污染 | **天然隔离** |
| 和文档那句"绿是对 commit 的事实" | 对不上 | **对上了** |

## 完整流程会变成

```
工作区有改动
  → 先建一个**候选 commit**（不挪 HEAD）
  → 对这个候选跑门禁（临时 worktree）
  → 过了 → 挪 HEAD 到它
```

这样"被验的"和"被提交的"是**同一个 commit 对象**,
而不是"同一个树在两个不同时刻的两次计算"。比现在更强。

## 代价

**每次门禁都要 `git worktree add`**(要写一遍工作树)。

- 现在:`cwd: dir`,直接用现有工作区,**零开销**
- 改后:每次多一次 `worktree add`

对小仓库(P 本身就要几秒)影响不大;对大仓库可能是几秒的额外开销。

**缓解**:调用方就在工作区里、且要验的就是工作区当前状态时,可以走
**快路径**(直接用 `dir`)。代价是"两个输入类型" —— 概念没那么干净。

## 为什么值得考虑

1. **修正文档与实现的不一致**:现在那句"绿 = 关于某个 commit 的事实"
   是**名义上的**,不是实现的
2. **并行的前提**:子 agent 在自己的 worktree 里产出 commit,
   父 agent **不需要访问那个 worktree** 就能批准
3. **"子给一个 commit 号"自然成立**:commit 是不可变的,
   改一个字节 sha 就变 —— 比"一段消息文本"强得多

## 一句话

> **门禁不该问"这个目录现在长什么样",该问"这个版本里有什么"。**
