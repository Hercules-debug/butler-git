## 一、这是什么

`butler-git` —— 一个 git 原生的**节点门禁**工具。零依赖(只要 `node` 和 `git`)。

核心概念三条:

```
节点(node)   = 一个**意图**:要达成什么(expect)
             + 预期改动 Δ
             + 检测程序 P

Δ            = 预期变化的**精确集合**(如 M:lib/a.mjs),实际改动必须精确等于它
P            = 一条命令,退出码 0 才算过

commit       = 达成时留下的**证据**,不可变、可重放
```

**绿 = 一个关于某个 commit 的事实。**

详细概念见仓库里的 `README.md` 和 `DESIGN.md` —— **先读它们**。

## 二、这次要改什么

**改"人的面"里那张图**(`bg tree` 的终端版 / `bg html` 的网页版)。

它给人的**观看体验**不对。下面说现象,不说怎么画。

### 现象 1:图的横轴没有意义

现在这张图按**父子关系**排布(谁拆给谁的),用实线连;同时用**黄色虚线**表示
另一种关系:

```
A.result == B.base   ->  B 是从 A 达成的那个版本开始的
```

**问题**:布局只认父子,所以那串虚线连接的节点被**摊平成横排**。

用真实数据看(仓库现在的图):

```
● root        butler-git 可用:插件自测通过
  ● t1          ...
  ● t2          ...
● gate2       空 Δ 达成时转录实际改动...
  ● gate2b      ...
● vis2        可视化:每个节点可追溯...
● graph1      HTML 改成图...
● flat1       删掉根门禁...
● approve1    子提议+父批准...
● toplevel1   顶层会话没有父 agent 时...
● cand1       子提议产出候选 commit...
● prompt1     提示词:教模型好的 P...
```

`vis2 → graph1 → flat1 → approve1 → toplevel1 → cand1 → prompt1`
是**一条完整的时间链**(七个节点首尾相连),但在图上它们是**七个并列的方块**,
看不出先后,虚线的意义也看不出来。

**用户的原话**:

> 我怀疑是不是应该 git commit 和 node 节点一起显示,直接显示成一个完整树。

> 我的理解是 git 应该是主干。

### 现象 2:节点不是一个"点",是一个"区间"

每个节点有这几样时间信息:

| 信息 | 在哪 | 含义 |
|---|---|---|
| **声明时刻** | `.bg/ledger.jsonl` 的 `ts` | 节点什么时候被声明 |
| **base** | 节点字段 | 从哪个 commit 开始干活 |
| **达成** | 节点字段 `result` | 哪个 commit 是它的证据(**未达成为空**) |

**它们不是同一个点。** 真实数据:

```
节点          base      达成       base 到达成之间夹了几个提交
root         ec936cd   f5d612a   3
t1           ec936cd   292f10f   1
t2           ec936cd   1b19ec0   2
gate2        f5d612a   195bebc   2
gate2b       f5d612a   f3251b5   1
(其余 9 个都是 1)
```

注意 `root`:它的 base 是 `ec936cd`,达成是 `f5d612a` —— **中间夹了 3 个提交**,
而那 3 个里面**就有 `t1` 和 `t2` 的提交**。

也就是说:

```
时间轴:  ec936cd ── t1 ── t2 ── root ── ...
             ↑                     ↑
          root.base            root 达成
             └──── root 的区间 ────┘
             t1、t2 都落在它里面
```

**用户的原话**:

> 而且,可能一个节点的 base 和通过时的 commit 中间还有别的 git commit

### 现象 3:节点树和 git 历史是**错位**的

节点树表达的是**意图结构**(谁拆给谁的):

```
root
├─ t1
└─ t2
```

git 历史表达的是**时间顺序**(谁先提交):

```
t1 → t2 → root        (t1 最先,root 最后)
```

**两者方向相反。** `root` 在节点树里是父亲,但在 git 历史里是**最后一个**提交的。

### 现象 4:`todo` 节点在图里没有位置

**用户的原话**:

> (甲) 声明早于提交:节点在 todo 时就存在(图里该显示),但 git 里还没有它

一个节点被声明时(`todo`),git 里**什么都没有**。它只有"声明时刻"。
达成之后才有 commit。

所以图要能表达"**声明了但还没做**"这件事。

## 三、用户的意图(总结)

1. **以 git 历史为主干** —— 时间轴就是提交顺序
2. **节点是主干上的东西**,但它是**一个区间**,不是一个点
   (从 base 到达成;未达成就只有起点)
3. **`todo` 节点也要显示** —— 它在主干上还没有 commit,但要看得见
4. **意图结构(父子)仍然要能看出来** —— 它和 git 顺序不是一个维度,别把两者混为一谈
5. 目标读者是**人** —— 这张图是给人看"这个项目在发生什么"的

## 五、怎么验收

**你的产出应该让人能这样看到效果:**

```bash
cd <仓库>
node bin/bg.mjs html        # 生成 .bg/tree.html,浏览器打开看
node bin/bg.mjs tree        # 或者直接看终端版
node bin/bg.mjs serve       # 或者起实时查看器(默认 127.0.0.1:8731)
```

**判断标准(由你判断怎么满足,但结果要满足):**

- 看那张图,能一眼看出**时间顺序**(谁先谁后)
- 能看出**节点是区间**(`root` 横跨了 `t1`、`t2`)
- 能看出**意图结构**(谁是父、谁是子),而不是和上面混在一起
- `todo` 节点有位置(现在仓库里全是绿的,你可以先建几个 `todo` 节点验证)
